<objective>
Wire the confirmation path end-to-end (BUY-03, BUY-04). In `_try_auto_buy`, after
`auto_buy()` returns True and the notify fires, obtain the live tab via
`plugin.get_active_tab()`, call `detect_order_confirmation(tab, platform)`, and enqueue
`("confirmed", link, order_id, ts)` when a non-None order_id comes back — otherwise log a
WARNING and fall back to the legacy `("purchased", link)` tag. Add the `("confirmed", ...)`
branch to `_dispatch_write` routing to `update_item_confirmed_sync`. In the Amazon and
BestBuy plugins, store `self._last_tab = tab` immediately before `place_order_guarded` and
override `get_active_tab()` to return `self._last_tab or self.driver.main_tab`.

Purpose: `purchased=1` is written only on a verified confirmation (`confirmed` tag), never
on a button click; on a missed confirmation the bot warns and uses the legacy path (no
silent failure, no double-buy).
Output: orchestrator wiring + 2 plugin overrides + orchestrator branch tests.

Critical: the `write_queue.put()` calls stay OUTSIDE any timeout context (the settle delay
lives inside detect_order_confirmation, NOT in _try_auto_buy) — forward-compat with the
Phase 21/22 per-item timeout per STATE.md PITFALLS #10.

Depends on Wave 1: update_item_confirmed_sync (Plan 01), detect_order_confirmation (Plan
02), get_active_tab() ABC default (Plan 03).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin tab → orchestrator → write queue | order_id from a retailer page flows through detection into a DB write |
| auto_buy success → DB write | the decision to write purchased=1 must require a verified confirmation, not a button click |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-08 | Repudiation | purchased write without confirmation | mitigate | purchased=1 via the confirmed tag requires a non-None order_id; the legacy fallback is logged at WARNING (no silent failure) — BUY-03 criterion 3 |
| T-19-09 | Tampering | double-buy from confirmation path | mitigate | mutually exclusive if/else: exactly one write_queue.put per successful auto_buy (Pitfall 5); asserted by test_no_double_buy_single_put |
| T-19-10 | Tampering | orphaned write under future timeout | mitigate | write_queue.put() kept OUTSIDE any timeout context; settle delay isolated inside detect_order_confirmation (PITFALLS #10) |
| T-19-11 | Info Disclosure | CVV in confirmation logs | mitigate | confirmation log line uses order_id only; self._cvv is set in a different code path and never logged adjacent to confirmation |
</threat_model>
