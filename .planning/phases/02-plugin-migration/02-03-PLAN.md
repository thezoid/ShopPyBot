<objective>
Wave 2: create `core/registry.py` — the plugin registry that auto-discovers `shopbot_plugin_*.py` files via `importlib`, routes item URLs to plugins by `domain_patterns`, and owns the lazy-launch lifecycle (CORE-03, CORE-04).

The registry implements D-09 (eager discovery, lazy browser launch): at construction it discovers and instantiates ALL `shopbot_plugin_*.py` plugin classes (cheap; reads `domain_patterns`), but `setup_for_items(items)` awaits `setup()` (launches Chrome) ONLY for plugins with ≥1 matching item. `route(url)` does substring matching of `domain_patterns` against `urlparse(url).hostname` (D-10). `teardown_all()` closes every launched plugin at shutdown.

Per success criterion 2 and CONTEXT.md discretion: non-matching `.py` files log a WARNING and are skipped; plugin import failures and `setup()` failures are logged and skipped — the bot never crashes on a single bad plugin (this is the import-of-arbitrary-disk-code trust boundary, modeled below).

Purpose: this is the discovery+routing+lifecycle core that makes plugins drop-in (CORE-03/04) and that `main.py` (Plan 05) drives.
Output: `core/registry.py`, `tests/test_registry.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugins/ on disk → registry importlib exec | THE phase trust boundary: `_discover_plugins` runs `exec_module` on every `shopbot_plugin_*.py` — arbitrary code execution from disk |
| item URL (config.yml) → route() | URLs originate from user-controlled config; parsed via urlparse for routing only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04 | Elevation of Privilege | _discover_plugins exec_module of plugins/shopbot_plugin_*.py | accept (documented) | Loading local Python files is equivalent to exec; for a personal bot on a trusted machine this is accepted. Mitigations in place: strict `shopbot_plugin_*.py` name filter (non-matching .py warned + skipped), import failures are log+skip not propagated. Community plugins must be code-reviewed before placement (PLUGIN_DEV.md note, Plan 06; formal policy is Phase 3 DOCS-02/03). |
| T-02-05 | Denial of Service | a malformed/malicious plugin raising at import or in setup() | mitigate | Import wrapped in try/except Exception → writeLog WARNING + skip; setup() failures in setup_for_items wrapped in try/except → log + skip. One bad plugin cannot crash the registry or the bot (success criterion 2). Verified by test_import_failure_skips. |
| T-02-06 | Tampering | route() parsing attacker-influenced URL strings | mitigate | route uses urlparse(url).hostname (not raw-URL substring) so query/path cannot spoof a host match (D-10). No eval of URL content. |
| T-02-07 | Information Disclosure | registry handling of config passed to plugins | mitigate | Registry passes the typed AppConfig through to plugin __init__ unchanged; it logs plugin filenames/errors only, never config values or credentials. |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs (importlib, inspect, pathlib, urllib are stdlib). No new deps. |
</threat_model>
