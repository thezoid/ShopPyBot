<dependabot_procedure>
Shared decision tree. Apply it identically to every Dependabot PR in this plan and in plan 05.
Do not deviate; record which branch was taken for each PR.

STEP 1, re-derive live state. `gh pr view <n> --repo thezoid/ShopPyBot --json state,mergeStateStatus,title,files,additions,deletions,headRefName`. If `state` is already `CLOSED` or `MERGED`, GitHub resolved it on its own: record that outcome and skip to STEP 6.

STEP 2, direction check (this is the supply-chain gate, not a formality). Read the PR title for the target version and read what master currently carries for the same package: `git show origin/master:requirements.txt` and `git show origin/master:pyproject.toml`. If master's version is EQUAL to or NEWER than the PR's target, the PR is superseded. Merging it would be a downgrade. Go to STEP 5. If master's version is OLDER, the PR moves master forward: go to STEP 3.

STEP 3, bring it up to date. `strict: true` requires the head to have absorbed the previous merge. These are Dependabot-authored PRs, so prefer Dependabot's own rebase over `gh pr update-branch`: post `gh pr comment <n> --repo thezoid/ShopPyBot --body "@dependabot rebase"`. Poll `gh pr view <n> --repo thezoid/ShopPyBot --json mergeStateStatus,headRefOid --jq '{s: .mergeStateStatus, h: .headRefOid}'` every 30 seconds, maximum 30 iterations (15 minutes), watching for `mergeStateStatus` reaching `CLEAN` or for `headRefOid` changing (which proves the rebase happened). Run the loop as a background Bash invocation; foreground `sleep` may be blocked.

STEP 3a, first timeout. If neither CLEAN nor a new head OID appears within 15 minutes, this is the Pitfall 5 pause signal. Record it, then try once more with `gh pr update-branch <n> --repo thezoid/ShopPyBot` and poll a second 15-minute window.

STEP 3b, second timeout. If it is still stale after the second window, do NOT grind. Record concrete Pitfall 5 evidence in 36-MERGE-LOG.md (the comment URL, whether any emoji reaction appeared, the unchanged head OID, and both timeout timestamps) and fall through to STEP 5 if and only if STEP 2's direction check would now classify it as superseded against current master. If it is genuinely still a forward move and cannot be rebased, STOP and escalate: 36-RESEARCH.md Assumption A2 flags this as an operator Settings change (Phase 38, SCAN-01), not something to retry autonomously.

STEP 4, merge. Wait for checks with `timeout 1200 gh pr checks <n> --repo thezoid/ShopPyBot --watch --interval 30 > /dev/null 2>&1`, then read terminal buckets with `gh pr checks <n> --repo thezoid/ShopPyBot --json name,bucket`. Buckets `pass` and `skipping` satisfy branch protection; CodeQL reporting `skipping` on a dependency-only PR is expected and is NOT a blocker (36-RESEARCH.md Pitfall 4). Then `gh pr merge <n> --repo thezoid/ShopPyBot --merge --delete-branch=false`. Do NOT pass `--admin`, `--squash`, or `--rebase`. On a `fail` bucket or a `timeout` exit code 124: record the state and STOP for escalation, since a red dependency bump on a just-proven-green master is real signal.

STEP 5, superseded-close. `gh pr close <n> --repo thezoid/ShopPyBot --delete-branch=false --comment "<reason>"`. The reason MUST name the package, the PR's target version, the version master already carries, and the word Superseded, following the PR #8 precedent from plan 01. A bare close does not satisfy MAIN-07's resolved-state bar with a checkable reason.

STEP 6, record and re-verify. Append one row to 36-MERGE-LOG.md: PR number, package, PR target version, observed master version, branch taken (merge or superseded-close or already-resolved), resulting state, and the exact command. After a MERGE (not after a close), `git fetch origin` and confirm the CI run for the new master SHA still schedules a non-empty jobs array with all conclusions `success`, using the same assertion shape as plan 03 task 3. A dependency bump that turns master red is caught here, one merge at a time, rather than at phase end.

STEP 7, recovery when STEP 6 finds master RED. This is not a generic executor deviation and must not be handled by improvisation. Do ALL of the following, in order. (a) Do NOT proceed to the next PR in the order; the sequence halts here. (b) Do NOT revert the merge, do NOT force-push, and do NOT amend or push a fix onto master or onto the merged PR's branch. (c) Do NOT reach for `--admin`: a red master is precisely what that flag would mask, and it is prohibited in this state exactly as it is in STEP 4. (d) Invoke the shared fix_forward_protocol above, starting at STEP F0, which re-reads the phase-wide counter out of 36-CI-EVIDENCE.md before incrementing. The budget of three is shared with plans 03 and 05 and does not reset for this plan. (e) If STEP F0's guard fires, or if three attempts are consumed without master returning green, STOP the phase, write the escalation into 36-CI-EVIDENCE.md, and do NOT start plan 05. This is the single sanctioned recovery path for a red master in this plan; CONTEXT.md's locked fix-forward policy governs it, not the executor's default deviation loop.
</dependabot_procedure>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dependabot-authored PR to master's dependency graph | Automated, unreviewed content proposing changes to the pins every later phase depends on |
| PR title and diff to the merge decision | The PR's own claimed target version is attacker-influenceable metadata and must be checked against the actual diff and against master |
| Dependabot service availability to phase completion | An external service's pause state can stall MAIN-07 for a non-correctness reason |
