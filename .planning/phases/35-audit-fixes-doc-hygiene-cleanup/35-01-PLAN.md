## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form → POST /items/remove | Untrusted, potentially cross-origin, state-changing (item removal) request crosses into the backend |
| Jinja2 template → rendered HTML attribute | The item link value is interpolated into a hidden form `value="..."` attribute |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-01-01 | Tampering | POST /items/remove (CSRF: cross-site form auto-submit triggering removal) | mitigate | `dependencies=[Depends(check_origin)]` on the route — identical CSRF guard used by every other mutating route; asserted by a new cross-origin 403 test in tests/test_web_security.py |
| T-35-01-02 | Tampering / Information Disclosure | Reflected XSS via the hidden `link` form value in dashboard.html | mitigate | Jinja2 default autoescaping escapes the value inside the HTML attribute (same reliance as the existing `{{ item[1] }}` interpolation); no raw/`\|safe` filter used |
| T-35-01-03 | Elevation / injection | `link` form field passed to BotService.remove_item | mitigate | Server-side validation: empty/missing link is a no-op (never reaches the DB layer); remove_item is a parameterized no-op-safe SQLite delete, matching the existing DELETE route's permissive behavior (ASVS V5) |
| T-35-01-SC | Tampering | Supply chain (package installs) | accept | No packages installed this plan — `python-multipart==0.0.32` (needed by `request.form()`) is already a declared `[web]` dependency; no new install surface |

Spoofing / Repudiation / Denial-of-Service dispositions: accept — localhost-bound single-operator tool with no auth system; consistent with the codebase's existing threat posture for the sibling DELETE route.
