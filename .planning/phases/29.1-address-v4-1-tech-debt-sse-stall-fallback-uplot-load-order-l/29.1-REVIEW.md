## Critical Issues

### CR-01: `setIndicator('live')` gated behind `_sseFallbackTimer` -- indicator can stick on 'Reconnecting' permanently

**File:** `web/templates/dashboard.html:636-640`

**Issue:** The `status` event listener calls `setIndicator('live')` only when `_sseFallbackTimer` is non-null (i.e., only when the watchdog has already fired and started the REST fallback). There is a reachable scenario where this is false but the indicator is 'reconnecting':

1. SSE stream has a transient error (`onerror` fires on line 647, sets indicator to 'reconnecting').
2. EventSource auto-reconnects in under 8 seconds; `onopen` fires (line 646, sets indicator to 'live') -- this path is fine.
3. BUT: some browsers defer `onopen` or skip it on a seamless reconnect. In those cases the first `status` event arrives with `_sseFallbackTimer === null`, so `setIndicator('live')` is never called, and the indicator remains 'Reconnecting' indefinitely while real SSE data renders correctly below it. The longer the page is open, the more likely a transient hiccup triggers this.

Additionally, if a custom proxy or server-side behavior emits a `status` event before completing the HTTP handshake in a way that prevents a clean `onopen` callback, the same stuck-indicator state arises.

The `if (_sseFallbackTimer)` guard was designed to stop the redundant REST polling; the `setIndicator('live')` call was collapsed into it unnecessarily.

**Fix:**
```javascript
es.addEventListener('status', function(e) {
  try {
    renderStatus(JSON.parse(e.data));
    _sseLastStatusTs = Date.now();
    setIndicator('live');          // always sync indicator on any received status event
    if (_sseFallbackTimer) {       // only teardown when the REST fallback is actually running
      clearInterval(_sseFallbackTimer);
      _sseFallbackTimer = null;
    }
  } catch (err) { /* ignore malformed SSE frame */ }
});
```

## Warnings

### WR-01: `test_watchdog_setinterval_in_sse_branch` does not verify what its name claims

**File:** `tests/test_sse_wiring.py:244-263`

**Issue:** The test name and docstring say "Watchdog setInterval appears inside the EventSource branch." What the test actually checks is that the string `SSE_STALL_MS` appears before the `else` branch. It does not verify that a `setInterval` call referencing `SSE_STALL_MS` exists, nor that the watchdog `setInterval` itself is inside the `if` block. If the watchdog were accidentally moved to the `else` branch (or removed entirely) but the `SSE_STALL_MS` constant declaration remained at the top (line 212, before the feature-detect), the test would still pass. This is a false-green risk: the test gives confidence it has not earned.

**Fix:** Assert on the watchdog setInterval pattern itself, positioned before the else branch:
```python
def test_watchdog_setinterval_in_sse_branch(client):
    resp = client.get("/")
    assert resp.status_code == 200
    text = resp.text
    detect_idx = text.find("typeof EventSource")
    assert detect_idx != -1
    sub = text[detect_idx:]
    else_match = re.search(r'\belse\b', sub)
    assert else_match is not None
    else_abs_idx = detect_idx + else_match.start()
    # Check that the watchdog setInterval (which uses SSE_STALL_MS) is inside the if block
    watchdog_idx = text.find("SSE_STALL_MS", detect_idx)
    assert watchdog_idx != -1, "SSE_STALL_MS usage not found after feature-detect"
    assert watchdog_idx < else_abs_idx, (
        "SSE_STALL_MS must appear before the else branch "
        "(i.e., inside the EventSource if block)"
    )
    # Also verify a setInterval is present in the if block
    watchdog_interval_idx = text.find("setInterval(function", detect_idx)
    assert watchdog_interval_idx != -1, "watchdog setInterval not found in SSE block"
    assert watchdog_interval_idx < else_abs_idx, (
        "watchdog setInterval must appear before the else branch"
    )
```

### WR-02: Watchdog `setInterval` has no teardown path and no stored handle

**File:** `web/templates/dashboard.html:623-630`

**Issue:** The outer watchdog `setInterval` (lines 623-630) runs at `POLL_MS` (2s) for the lifetime of the page, with no stored handle and no `clearInterval` ever called on it. Unlike `_sseFallbackTimer` (which is cleaned up on recovery), this timer fires unconditionally forever, re-checking the stall condition on every tick. This is a minor correctness concern: if `pollStatus` / `pollLogs` from the fallback path themselves block for an extended period, the watchdog can fire overlapping closure evaluations. More concretely, the watchdog can fire while the fallback timer is being torn down, observe `_sseFallbackTimer` is null, and immediately restart it before the recovery path has finished setting the indicator -- creating a one-tick double-restart window.

The standard pattern is to store the watchdog handle so it can be cancelled when the page tears down (e.g., `visibilitychange` or `beforeunload`) or at minimum to skip watchdog work when it detects the fallback is already active and recovery is in progress.

**Fix (minimal):** Store the watchdog handle so teardown is possible:
```javascript
var _sseWatchdogTimer = setInterval(function() {
  if (Date.now() - _sseLastStatusTs > SSE_STALL_MS) {
    setIndicator('reconnecting');
    if (!_sseFallbackTimer) {
      _sseFallbackTimer = setInterval(function() { pollStatus(); pollLogs(); }, POLL_MS);
    }
  }
}, POLL_MS);
```
Then on page unload or stream teardown:
```javascript
clearInterval(_sseWatchdogTimer);
```

### IN-02: `var` hoisting for `_sseLastStatusTs` and `_sseFallbackTimer` inside the SSE `if` block is misleading

**File:** `web/templates/dashboard.html:617-618`

**Issue:** `var _sseLastStatusTs` and `var _sseFallbackTimer` are declared with `var` inside a block-level `if` statement. In JavaScript, `var` declarations are hoisted to the enclosing function (or script global) scope, not to the block. These variables are effectively globals accessible anywhere in the `<script>` block, including the `else` branch and any other code below. The intent appears to be that they are scoped to the SSE active path, but they are not. A future maintainer could accidentally read or mutate `_sseFallbackTimer` from the polling-fallback `else` branch without realizing it was supposed to be SSE-path-local state.

**Fix:** This is a style/maintainability concern for vanilla JS with no `let`/`const` available inside an `if`. The simplest fix is to wrap the entire `if (typeof EventSource !== 'undefined')` block in an IIFE to give it true function scope, or to use `let` (already used elsewhere in the same script):

```javascript
if (typeof EventSource !== 'undefined') {
  let _sseLastStatusTs = Date.now();
  let _sseFallbackTimer = null;
  // ... rest of SSE block
} else {
  // ...
}
```

`let` is already used throughout this `<script>` block (e.g., `let series` at line 441), so this is consistent with the existing style.
