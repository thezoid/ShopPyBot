changes actually closed the alerts they were written to close.

Purpose: the phase's verification bar is that a finding counts as resolved only when the alert

Output: master carrying every file change from 38-02 and 38-03, and a summary holding the
before-and-after API state for alerts 3, 4, 5, for the ci.yml workflow-permissions findings, and for
Dependabot 13.

This plan changes no files. Direct pushes to master are not authorised; the change reaches master
through a pull request.

**Shell contract for this plan.** Every fenced block below is POSIX shell, run in Git Bash as ONE
invocation. There is no PowerShell in this plan and none may be added to it. Three properties are
load-bearing and each fenced block is written to hold all three:

- `set -eu` opens every block, and every stop is an explicit `exit 1` after a VALUE assertion. An
  exit-code check is never used where a value check is possible.
- A guard and the mutation it authorises live in the SAME fenced block. Shell variables do not
  survive between harness calls and a guard submitted as a separate call from its mutation gates
  nothing, so anything a guard depends on is re-derived inside the block that consumes it. This is
  why `gh pr merge` sits inside the check-runs gate rather than after it.
- `rtk proxy` is load-bearing on every `gh` and every value-asserted `git` read. The mandatory rtk
  hook rewrites a bare `gh api` to `rtk gh api`, whose filter DROPS the HTTP status line these
  guards assert on, and rewrites a bare `git status --porcelain` to `rtk git status --porcelain`,
  which prints the 2-byte string `ok` on a clean tree so every emptiness test against it is
  inverted. Both measured. Mutating git commands (`fetch`, `merge`, `checkout`) are left bare.

Dispatch expectation, not a defect: the harness auto-mode classifier INTERMITTENTLY DENIES
`gsd-executor` dispatch for plans that merge a pull request, and this plan merges one. It denied

`.planning/STATE.md`'s Phase 37 carry-forward records the same expectation. Because the denial is
intermittent, a dispatch that succeeds is not evidence the hazard is gone and a dispatch that fails
is not a fault in this plan. Either way the workaround is the same and is the default here: do not
retry the dispatch and do not re-request it, run the three tasks inline in the main thread. Inline
execution produces no per-task commits and no per-plan `STATE.md` write, so when Task 3 finishes,
