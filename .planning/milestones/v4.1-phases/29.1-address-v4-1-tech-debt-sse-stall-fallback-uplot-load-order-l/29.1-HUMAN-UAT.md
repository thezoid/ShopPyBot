### 2. SSE-01/02 stall fallback timing
expected: Drop the SSE stream without closing it (e.g., pause the server poll loop). Within ~8s the `#sse-indicator` flips to "Reconnecting" and REST fallback requests to `/api/status` + `/api/logs` resume at ~2s cadence. Restore the stream: on the next `status` event the indicator returns to "Live" and the fallback polling stops.
result: [PASS - 29.1-UAT-2, verified 2026-08-01 via live browser UAT session. On a stalled stream the indicator flipped to "Reconnecting" with `#sse-dot` class `status-dot reconnecting`, exactly one fallback timer started, and `/api/status` + `/api/logs?n=500` pairs fired at ~2s cadence. On recovery the indicator returned to "Live" and `_sseFallbackTimer` went back to null. Test-recipe nuance: setting `_sseLastStatusTs = 0` alone does not reliably trip the watchdog on a healthy stream because live ~1s status frames overwrite the timestamp before the 2s watchdog tick evaluates it; closing the EventSource first makes the trigger deterministic. That is a property of the test recipe, not a product defect: the watchdog behaved exactly as specified.]

### 3. OBS-07 repeated log lines after a filter repaint
expected: After a log filter repaint, repeated identical SSE log lines all appear. Only the single backfill->SSE boundary duplicate is silently dropped; legitimately repeated consecutive bot messages are never suppressed.
result: [PASS - 29.1-UAT-3, verified 2026-08-01 via live browser UAT session. Deterministic console proof: `renderLogLines` with two identical lines rendered 2, armed the one-shot flag, the first appended duplicate was swallowed (still 2), the second appended (3), proving the dedup is a strict one-shot at the backfill boundary only. Realistic path also confirmed: after a WARNING-level filter repaint, 66 identical repeated lines all rendered, none suppressed. The filter gate is correctly anchored to the second bracket: `lineMatchesFilters('[INFO][amazon] saw [bestbuy] in text','','','bestbuy')` returns false.]
