## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| retail confirmation page → orchestrator | Page state (confirmed vs. payment-failure) is untrusted; only a real `order_id` is the idempotency anchor |
| SQLite marker state → retry guard | The write-ahead marker crosses the crash-durability boundary (must be on disk before the click) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-02 | Tampering / Repudiation / Integrity | place-order double-submission via naive retry-on-any-failure | mitigate | DB write-ahead marker (`place_order_attempted_at`) + `_PossiblyPlaced` non-retryable guard in `_pre_attempt_check`; retry aborts when marker set and order_id is None (the fix itself) |
| T-30-02b | Repudiation | silent drop of an attempted-but-unconfirmed order | mitigate | `_try_auto_buy` fires a `possibly_placed` operator alert (never silently returns) so a placed-but-unconfirmed item is reviewed, not lost |
| T-30-03 | Spoofing | false-positive auth proceeding through retries | mitigate | login-stage short-circuit (should_retry predicate) stops cart-retry after a single verified-failed login and alerts (`login_failed`) instead of looping |
| T-30-V7 | Information Disclosure | credential/key leak via exception text | mitigate | all new handlers log `exc.__class__.__name__` only; never `str(exc)`; never log credentials or the 2captcha key |

No package-manager installs occur in this plan (phase adds zero dependencies) — no supply-chain (`T-30-SC`) checkpoint required.
